# Infraestrutura AWS

> Este projeto também é material de estudo: cada decisão traz o **porquê** e, quando relevante, o que mudaria com mais orçamento. Os valores de custo são estimativas em `us-east-1` para tráfego baixo e devem ser conferidos na calculadora da AWS.

## Problem Statement

A API (ver `backend.md`) e o futuro front em React só rodam localmente em Docker. Para o portfolio cumprir seu papel — ser acessado por recrutadores e demonstrar conhecimento sólido em nuvem — ele precisa estar publicado em um domínio próprio (`.info`, registrado na Hostinger), com HTTPS, deploy automatizado e infraestrutura reproduzível. As restrições são fortes: cerca de US$ 100 de crédito e um teto de **R$ 60/mês (~US$ 11)**, o que exclui a arquitetura "de livro" (ALB + ECS + RDS custaria US$ 40+/mês). O banco fica fora da AWS, no Neon, para tirar esse custo da conta.

## Solution

- **Front (React SPA)**: arquivos estáticos em S3 privado, servidos pelo CloudFront no domínio raiz (`<dominio>.info`).
- **API**: a mesma imagem Docker de hoje roda no **AWS Lambda** (via Lambda Web Adapter), exposta por um **API Gateway HTTP API** em `api.<dominio>.info`. Paga-se por requisição; parada, custa ~zero.
- **Banco**: **Neon** (Postgres serverless, região AWS `us-east-1`), fora da conta AWS.
- **Uploads**: bucket S3 privado, servido pelo mesmo CloudFront do front em `<dominio>.info/uploads/*`.
- **DNS e certificados**: Route 53 + ACM, tudo gerenciado por **Terraform**, executado via Docker como o resto do projeto.
- **CI/CD**: GitHub Actions autenticando por **OIDC** (sem chaves AWS guardadas): testa, publica a imagem no ECR, roda migrations no Neon, atualiza a Lambda e faz smoke test.
- **Guardas de custo e operação**: AWS Budgets, Cost Anomaly Detection, alarme de erros da API e backup diário do banco no S3.
- Custo esperado: **~US$ 1–2/mês**, bem abaixo do teto; os créditos duram muito além do previsto.

## User Stories

### Visitante
1. As a visitor, I want to open the portfolio at `https://<dominio>.info`, so that I can see the owner's work on a real domain.
2. As a visitor, I want every page served over HTTPS with a valid certificate, so that the site is trustworthy.
3. As a visitor, I want the site to load fast from Brazil, so that I don't give up waiting.
4. As a visitor, I want deep links of the SPA (e.g. `/projetos`) to work on refresh, so that shared links don't break.
5. As a visitor, I want images (profile photo, screenshots) to load from the same domain, so that nothing is blocked by the browser.
6. As a visitor, I want a missing image to return a real 404, not the SPA page, so that broken references are visible.
7. As a visitor, I want the CV download to work in production, so that I can keep it.
8. As a visitor, I accept that the first request after a long idle period may take ~1–3 s, so that the owner pays close to zero.

### Admin
9. As the admin, I want to log in from `https://<dominio>.info` against `https://api.<dominio>.info`, so that the refresh cookie keeps working (same site).
10. As the admin, I want uploads up to 4 MB to be accepted and stored durably, so that images survive deploys.
11. As the admin, I want login brute-force to be limited even with many Lambda instances, so that my account stays protected.
12. As the admin, I want my real IP (not a forged header) to be used for rate limiting, so that attackers can't bypass it.

### Operador / desenvolvedor
13. As the operator, I want the whole AWS setup declared in Terraform, so that it is reproducible and reviewable.
14. As the operator, I want to run Terraform through Docker via make targets, so that I install nothing locally.
15. As the operator, I want Terraform state stored remotely in S3 with locking and encryption, so that state is safe and never corrupted by concurrent runs.
16. As the operator, I want a one-time bootstrap for the state bucket, so that the chicken-and-egg problem is solved explicitly.
17. As the operator, I want to authenticate locally via IAM Identity Center (SSO), so that I never create long-lived access keys.
18. As the operator, I want DNS for the domain hosted in Route 53, so that the apex can point to CloudFront and certificates validate automatically.
19. As the operator, I want clear instructions to switch the nameservers at Hostinger, so that the domain delegation is a single manual step.
20. As the operator, I want secrets (JWT keys, database URLs) kept in SSM Parameter Store and never in git or GitHub, so that there is one source of truth.
21. As the operator, I want JWT secrets generated by Terraform, so that nobody has to invent or copy them.
22. As the operator, I want budget alerts by email at 50%, 80% and 100% of US$ 11, so that I learn about cost before it hurts.
23. As the operator, I want cost anomaly detection enabled, so that unusual spend is flagged automatically.
24. As the operator, I want every resource tagged with project and environment, so that I can filter costs.
25. As the operator, I want an email alarm when the API starts returning errors, so that I know production is broken.
26. As the operator, I want API logs in CloudWatch with a short retention, so that I can debug without paying for old logs.
27. As the operator, I want a daily database backup in S3 with automatic expiry, so that content can be restored even beyond Neon's free restore window.
28. As the operator, I want the restore procedure documented and tested once, so that backups are known to work.
29. As a developer, I want every push to `main` touching the API to be tested, built, migrated and deployed automatically, so that deploys are boring.
30. As a developer, I want CI to authenticate to AWS with OIDC and least-privilege roles, so that a leaked workflow cannot do more than its job.
31. As a developer, I want migrations to run against Neon's direct connection before the new code goes live, so that code never runs against an old schema.
32. As a developer, I want a post-deploy smoke test, so that a broken deploy is detected immediately.
33. As a developer, I want the production image to contain only the app and its runtime dependencies, so that cold starts are faster.
34. As a developer, I want the same image to run locally and on Lambda, so that production behavior matches development.
35. As a developer, I want the local Postgres major version to match Neon's, so that "works locally, breaks in production" bugs don't come from version drift.
36. As a developer, I want the web hosting ready before the web app exists (placeholder page), so that the domain works from day one.
37. As a developer, I want `terraform fmt`/`validate` in a make target, so that infra code is checked like app code.
38. As a reader of the repo, I want an ADR explaining why the API runs on Lambda and when to move it, so that the trade-off is explicit.

## Implementation Decisions

### Conta, região e acesso
- **Região única `us-east-1`**. Por quê: é a mais barata, é obrigatória para certificados usados pelo CloudFront, e a latência não pesa (o CloudFront serve o front a partir de edges no Brasil; a API tem pouco tráfego). O Neon é criado na mesma região para a Lambda falar com o banco sem cruzar continentes.
- **Acesso humano via IAM Identity Center (SSO)**, com login pelo AWS CLI em container. Por quê: credenciais temporárias; nenhuma access key de longa duração no disco.
- **Um só ambiente (produção)**. O Terraform recebe nome de ambiente como variável, mas staging não é construído (dobraria custo).
- **Tags padrão** (`project`, `env`, `managed-by=terraform`) aplicadas por `default_tags` do provider.

### Terraform
- Código no diretório `infra/` do monorepo, com duas raízes:
  - **bootstrap**: bucket de estado (versionado, criptografado, acesso público bloqueado). Aplicado uma vez, com estado local — resolve o "ovo e galinha" de onde guardar o estado do próprio Terraform.
  - **main**: todo o resto, com backend S3 e **lock nativo do S3** (`use_lockfile`, Terraform ≥ 1.10). Por quê: dispensa a tabela DynamoDB que tutoriais antigos usam.
- Arquivos por assunto (DNS, web, API, uploads, CI, observabilidade, custo), **sem módulos próprios**: um único consumidor não justifica a abstração.
- Versões fixadas: Terraform e provider AWS na major mais recente estável.
- **Estado é sensível**: contém os segredos gerados e lidos (JWT, URL do banco). O bucket de estado é criptografado e só o papel de administrador acessa.
- Executado via imagem Docker oficial do Terraform, com targets no Makefile (`tf-init`, `tf-plan`, `tf-apply`, `tf-fmt`) e login SSO via container do AWS CLI (`aws-login`).
- Infra é aplicada localmente pelo operador; plano/aplicação em CI fica fora de escopo.

### DNS e certificados
- **Route 53 hosted zone** para `<dominio>.info` (~US$ 0,50/mês). Por quê: permite registro ALIAS no domínio raiz apontando para o CloudFront (CNAME no apex é proibido pelo protocolo DNS) e validação automática de certificados. O registro continua na Hostinger; lá só se trocam os nameservers para os da hosted zone (passo manual documentado).
- **ACM**: um certificado para `<dominio>.info` (CloudFront) e um para `api.<dominio>.info` (API Gateway), ambos em `us-east-1`, validados por DNS.

### Web (SPA) e uploads — uma distribuição CloudFront
- **Bucket do web** privado, acessado só pelo CloudFront via **OAC** (Origin Access Control). Por quê: o bucket nunca fica público; o CloudFront é a única porta.
- **Bucket de uploads** privado, também via OAC, servido pela mesma distribuição no caminho `/uploads/*`. Por quê: imagens no mesmo domínio do site (sem problemas de CORS/CORP), um certificado e uma distribuição a menos. Os objetos ficam sob o prefixo `uploads/` no bucket, pois o CloudFront repassa o caminho completo à origem.
- Mídia apagada pode continuar servida pelo cache do CloudFront até o TTL expirar; aceitável, pois as keys são UUIDs nunca reutilizados e ninguém mais as referencia.
- **Rewrite de SPA via CloudFront Function** apenas no comportamento padrão (rotas sem extensão → `index.html`). Por quê: as "custom error responses" do CloudFront valem para a distribuição inteira e transformariam um upload inexistente em página do SPA com status 200.
- **Response headers policy** com HSTS, `X-Content-Type-Options`, `Referrer-Policy` e `frame-ancestors`/`X-Frame-Options`.
- Cache: `index.html` sem cache longo; assets com hash de build e uploads (chave UUID imutável) com cache longo.
- Enquanto o `apps/web` não existe, o Terraform publica um `index.html` provisório.
- Custo: dentro da cota gratuita permanente do CloudFront para esse volume.

### API — Lambda + API Gateway HTTP API
- **Lambda com imagem de contêiner**, arquitetura **arm64** (Graviton: mais barato por ms), memória 1024 MB (na Lambda, CPU escala com memória; argon2 e o boot do Nest precisam de CPU). Sem provisioned concurrency (custo fixo).
- **Lambda Web Adapter** incluído na imagem: traduz eventos da Lambda em HTTP para o servidor Express/Nest existente. Por quê: zero reescrita e a mesma imagem roda no compose local e na Lambda — portabilidade, sem handler proprietário. O readiness check do adapter é por **TCP** (porta aberta), não pelo `/health`: assim o cold start não depende de uma ida ao banco.
- **Sem VPC**: o banco (Neon) e os serviços AWS usados são acessíveis pela internet com TLS/IAM. Por quê: VPC exigiria NAT Gateway (~US$ 32/mês) para sair para a internet.
- **API Gateway HTTP API** com domínio customizado `api.<dominio>.info`. Por quê não Function URL + CloudFront: o OAC com Function URL exige que o cliente envie o hash do corpo em POST/PUT, o que complica uploads; o HTTP API já dá domínio, TLS e **throttling por rota**, por centavos por milhão de requisições.
- **Throttling no API Gateway**: limite padrão por rota (guarda de custo contra abuso) e limite mais baixo em `/auth/login` e `/auth/refresh`. É global (não por IP) — complementa o limite por IP da aplicação.
- **CloudWatch Logs** da Lambda com retenção de 14 dias (os logs já saem em JSON em produção).
- **O Terraform cria a função, mas não gerencia a versão da imagem** (ignora mudanças no `image_uri`): quem troca a imagem é o pipeline. Por quê: separa "infraestrutura" (Terraform) de "release" (CI), evitando que um `apply` reverta um deploy.
- **ECR** com lifecycle mantendo as últimas 10 imagens e scan na publicação.

### Adaptações na API (código)
- **Driver S3 do storage** (`STORAGE_DRIVER=s3`), usando o SDK v3 e as credenciais da role da Lambda (nenhuma chave em env). O banco continua guardando só a key; a URL pública passa a vir de uma config própria de base de URLs de upload (no driver local, continua `PUBLIC_URL/uploads`). Upload segue passando pela API para manter a validação por magic bytes.
- **Limite de upload de 5 MB → 4 MB**. Por quê: payload síncrono da Lambda é de 6 MB e binários trafegam em base64 (+33%).
- **Endpoint `GET /health`** público: responde 200 após um `SELECT 1` no banco. Usado pelo smoke test (não há sonda periódica, para não impedir o Neon de hibernar).
- **`TRUST_PROXY` vira número de saltos** (padrão 0; produção 1). Por quê: com `true`, o Express confia em todo o `X-Forwarded-For` e o cliente pode forjar o IP para escapar do rate limit. Com 1, usa o endereço adicionado pelo API Gateway.
- **Rate limit da aplicação persistido no Postgres**, restrito às rotas sensíveis (login, refresh, contato, CV). Por quê: cada instância da Lambda tem memória própria e efêmera; contador em memória não protege. O limite global genérico deixa a aplicação e passa para o API Gateway.
- **Migrations fora do runtime**: `prisma migrate deploy` roda no pipeline contra a conexão **direta** do Neon; a imagem de produção deixa de conter o Prisma CLI e a etapa de migrate no start. Por quê: imagem menor (cold start melhor) e nunca duas instâncias migrando ao mesmo tempo.
- **Conexões Neon**: a aplicação usa a string **pooled** (PgBouncer, host `-pooler`) — adequada a muitas conexões curtas de Lambdas; migrations e backup usam a **direta** (recursos de sessão que o pooler não suporta). TLS obrigatório (`sslmode=require`); certificados do Neon são públicos, sem bundle de CA.
- **Postgres local alinhado à major estável do Neon** (verificada na criação do projeto Neon); o compose fixa essa major.
- O compose de produção previsto antes (para EC2) deixa de existir.

### Segredos
- **SSM Parameter Store (SecureString, gratuito)** é a fonte única:
  - JWT access/refresh: gerados pelo Terraform (`random_password`) e gravados no SSM.
  - URLs do Neon (pooled e direta): criadas no console do Neon e gravadas no SSM por um target do Makefile (valor digitado, nunca em arquivo versionado).
- A Lambda recebe os valores como **variáveis de ambiente** (criptografadas em repouso pela chave gerenciada da AWS), lidas do SSM pelo Terraform. Por quê não Secrets Manager: US$ 0,40/segredo/mês e latência no cold start sem ganho aqui.
- O CI lê a URL direta do SSM via OIDC na hora de migrar/fazer backup — **nenhum segredo de banco no GitHub**; o GitHub guarda só identificadores não sensíveis (ARN das roles, região).

### CI/CD (GitHub Actions)
- **Provedor OIDC do GitHub** registrado na conta; roles com trust restrito ao repositório e à branch `main`, permissões mínimas por workflow (API: push no ECR, update da função, leitura dos parâmetros necessários; backup: leitura do parâmetro da URL direta e escrita no prefixo de backups).
- **Workflow da API** (push em `main` que toque `apps/api` ou workflows): lint + e2e (Postgres como serviço do job) → build da imagem **arm64** (runner ARM nativo do GitHub, gratuito em repositório público; senão QEMU) → push no ECR → `migrate deploy` no Neon → atualização da imagem da Lambda → smoke test.
- **Workflow de backup** (diário, agendado): `pg_dump` pela conexão direta → bucket de backups (criptografado, lifecycle apaga após 30 dias).
- **Workflow do web**: fora de escopo (nasce com o `apps/web`); a role e o bucket já ficam prontos.

### Observabilidade e custo
- **AWS Budgets**: orçamento mensal de US$ 11 com alertas por e-mail em 50/80/100% (reais) e 100% (previsto). Importante: o Budgets **alerta, não bloqueia** — a AWS não tem teto rígido nativo.
- **Cost Anomaly Detection** com assinatura por e-mail.
- **Alarme CloudWatch** em erros/5xx da API → tópico SNS → e-mail (dentro da cota gratuita de alarmes).
- Estimativa mensal: Route 53 ~US$ 0,50; API Gateway, Lambda, S3, ECR, CloudWatch, CloudFront: centavos ou dentro das cotas gratuitas; **total ~US$ 1–2**.

### Makefile (novos targets)
- `aws-login`, `tf-init`, `tf-plan`, `tf-apply`, `tf-fmt` (fmt + validate), `tf-bootstrap`, `db-secrets` (grava URLs do Neon no SSM), `smoke` (smoke test contra a produção). Todos via containers.

## Testing Decisions

- **Um bom teste** verifica comportamento observável por fora (HTTP), não detalhes internos. Isso vale para a API e para a infraestrutura publicada.
- **Seam 1 — e2e HTTP da API (existente)**, cobrindo as adaptações:
  - rate limit persistido: duas instâncias da aplicação apontando para o mesmo banco compartilham o contador (a segunda recebe 429 após o limite atingido na primeira);
  - `X-Forwarded-For` forjado não muda a chave do rate limit com `TRUST_PROXY=1`;
  - `/health` responde 200 com banco disponível;
  - upload acima de 4 MB → 413.
  - O driver S3 não é testado no e2e (exigiria emular a AWS); é coberto pelo smoke test.
- **Seam 2 — smoke test pós-deploy** contra produção (target `smoke` e etapa do pipeline): `/health` 200; `/portfolio` 200; `/docs` 404; web raiz 200 com HSTS; rota profunda do SPA 200; `/uploads/<inexistente>` 404; CORS permitindo apenas a origem do site.
- **Checagem estática da infra**: `terraform fmt -check` e `validate` (target `tf-fmt`).
- Restore do backup executado manualmente uma vez em um branch do Neon e documentado.
- Prior art: suites e2e em `apps/api/test` e o harness `createApp`.

## Out of Scope

- Aplicação `apps/web` e seu workflow de deploy (apenas hosting e role prontos).
- Ambiente de staging e branches de preview do Neon.
- Terraform em CI (plan em PR / apply automático).
- AWS WAF (custo fixo mensal); proteção fica em throttling do API Gateway + rate limit da aplicação.
- Provisioned concurrency / aquecimento da Lambda.
- Multi-região, Multi-AZ, disaster recovery além do backup diário.
- Registro de `www.` e redirecionamentos de domínio.
- Gerenciamento do Neon via Terraform (projeto criado no console).
- Monitoramento sintético periódico (impediria o Neon de hibernar).

## Further Notes

- **Caminho de evolução** (ADR 0001): com orçamento maior ou tráfego constante, a API migra para ECS Fargate atrás de um ALB, com RDS ou mantendo o Neon; a imagem já é a mesma. Gatilhos: cold start inaceitável, uploads > 4 MB, tráfego contínuo que torne o custo por requisição maior que o de uma tarefa sempre ligada.
- Esta spec substitui, para produção, os seguintes pontos de `backend.md`: limite de upload (4 MB), `TRUST_PROXY` (saltos), rate limit global (API Gateway) e migrations no start do container (agora no pipeline).
- O domínio `.info` costuma ter renovação mais cara que o primeiro ano na Hostinger; isso fica fora do orçamento AWS.
- Novas contas AWS podem ter cotas baixas de concorrência da Lambda; suficiente para este tráfego, mas vale conferir em Service Quotas.
- Passos manuais inevitáveis (documentados): ativar IAM Identity Center, trocar nameservers na Hostinger, criar o projeto no Neon, confirmar as assinaturas de e-mail do SNS/Budgets.
